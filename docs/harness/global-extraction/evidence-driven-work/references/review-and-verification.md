# Review, verify and refine

Independent review is required for consequential plans/changes/boundaries where
the host supports it. Otherwise perform labelled self-review and actual checks,
record independent review NOT RUN and its residual gap, and preserve any stricter
project acceptance gate. Continue unaffected authorised work. Use
fresh reviewers without parent conversation history where supported. Give only the
current user outcome, constraints, relevant actual source/diff, factual evidence,
rubric and completion condition. Exclude suspected defects, previous verdicts and
preferred winners for a fresh discovery pass. Relevant product requirements still
belong in the packet; withholding them is not useful blindness.

Do not send a verdict-bearing handoff to a reviewer merely because normal workers
must read it. Provide a sanitised fact-only review brief instead. Label shared
history/model limitations and contextual follow-up accurately. A recheck by the
same reviewer is not a second independent trial. Masks/neutral labels can reduce
framing in preference comparisons but cannot remove shared model biases.

Trace each assigned subsection from input through authority/state transition to
visible result and failure/recovery. Review plans for user purpose, scope, dependency,
feasibility, maintenance, contradictory promises and measurable acceptance. Review
code for correctness, regressions, security boundaries and missing behavioral tests.
Do not report 'reviewed' from spawning an agent before receiving/reconciling findings.

Parent reconciles against real sources and reproduction. Fix confirmed findings,
explain evidence-backed disagreements and rerun affected checks. Challenge incorrect
grading as well as faulty code. A passing test can encode the wrong requirement.

For new production behavior/bugs, reproduce red, implement green, then refine.
Cover affected unit/integration/user flows and denied/concurrent/disconnect/return
paths where relevant. Use installed native checks; browser checks must execute real
interactions against the real service/storage when that is the claim. Builds/mocks
are different evidence. Verify actual screenshot dimensions and visible contents.

Apply specialist security guidance to changed input/auth/secret boundaries; check
secrets, dependencies and final diff before commits/releases as project rules require.
Use native checks for docs/configuration and real rendering for visual artifacts;
do not manufacture application test coverage for prose. Report exclusions/gaps.

End a lane when acceptance is demonstrated and material findings are resolved.
Reopen it for relevant changes or unresolved evidence. No endless review rounds,
unrelated suite repetition or claim that confidence replaces inspection.
