# Evidence-driven work

This personal workflow extracts reusable A2/A3 methods. It is owner-requested
working policy, not a claim that more agents or instructions universally improve
quality. Current user goals, applicable project rules and real evidence govern.

## Required recurring loop

For every meaningful phase/section/subsection, identify the user outcome and an
observable acceptance criterion; inspect actual relevant artifacts and instructions.
Return to the relevant methods and evidence at entry, after changed assumptions,
failed checks or review findings, and before completion/commit. Maintain granular
records rather than one aggregate PASS. Routine micro-edits can share a bounded
checkpoint; do not inflate them into experiments.

1. Name the uncertainty or defect, current version and evidence that could change
   the choice. Check dependencies, ownership and unrelated edits.
2. For a material choice with credible alternatives, compare them under a common
   task and predeclared criteria. Use meaningful comparisons often, including
   matched A/B for consequential agent/prompt/harness choices when executable.
   Follow [comparison and research](references/comparison-and-research.md).
3. For consequential design/implementation/authority boundaries, require independent
   review without previous chat history where supported. Provide a sanitised
   factual packet, not previous verdicts or a preferred winner. Follow
   [review and verification](references/review-and-verification.md). If independent
   review is unavailable, label self-review/actual checks and independent review
   NOT RUN, with the residual gap; never silently waive a stricter project gate.
4. Check actual sources, code/runtime and reviewer reproductions yourself. Refine
   confirmed issues, recheck affected paths and reconcile disagreements. Do not
   automatically trust a skill, paper, subagent, test or your initial design.
5. Record requirement, alternatives/method, actual conditions/result, finding,
   revision, affected checks and residual gaps in the project's existing notes.
   Keep a compact current handoff and focused commits where relevant. See
   [evidence and continuation](references/evidence-and-continuation.md).

Use research, prototype, test, review and refine cycles frequently where useful,
including subsections inside phases. Once relevant acceptance is demonstrated and
material issues resolved, stop that lane. No fixed trial/agent/technique quota.

## Skills and tools

Select from tools and skills actually available in the running session. Use focused
research, API documentation, product planning, UI, debugging, security, testing,
artifacts and evaluation skills when the task benefits; read their instructions
and relevant references, then assess them critically. Do not load the entire
catalogue, install bundles, pin stale models or pretend names imply availability.
Native agents are preferable to installing another orchestration system.

Use bounded parallel research/exploration/review where independent. Give workers
explicit non-overlapping ownership and warn they share the workspace. Parent owns
reconciliation and final verification. Respect actual authorisation, sandbox and
credential boundaries; this skill grants no extra external permissions.

## Evidence boundaries

Technical comparison, qualitative design/model review, agent-harness A/B, native
browser check, device trial and real-user A/B are different evidence. Preserve
failed/aborted/infrastructure outcomes; never turn hypothetical protocols into
completed studies. Mark inaccessible tools, participants or environments honestly
and continue independent authorised work. Do not invent demand, superiority,
performance, personal experience or grade guarantees.

Provenance and current source limits: [research basis](references/research-basis.md).
Read it when changing this workflow or making a claim about agent effectiveness;
normal project work does not need to reopen every paper.
