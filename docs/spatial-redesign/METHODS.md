# How this redesign used the agent methods

## The observed failure, not a technique quota

The owner reported that the places lacked useful purposes despite an earlier
technically checked implementation. Source inspection then found separate physical
seats, logical game participation and global work cards. The new owner expectation
changes those relationships; existing tests deliberately preserve some old ones.
The current loop must therefore revisit purpose and acceptance, not merely make
the old suite pass again.

## What transfers from current sources

[Google Harness2](https://arxiv.org/html/2610.14224v1),v1, sections2.2–2.3, describes
contrastive proposal/probing/composition and retaining scoped lessons. Here we
proposed distinct product practices, probed source/geometry and negative transfers,
then composed a smaller conditional direction. This borrows a method; it is not a
replication of the paper, an executed Harness2 framework or a new performance claim.
The previous four agent diagnostics retain their original scope.

[LangChain's loop engineering](https://www.langchain.com/blog/the-art-of-loop-engineering),
16June2026, distinguishes execution, verification, event-driven operation and
harness improvement. Its discussion also leaves audience/framing judgment to
people. Here the owner's feedback triggers a change in the task's acceptance
criteria: a room must help a concrete task, not merely exist and pass tests.
This is a manual project improvement loop, not a newly installed background service.

[LangChain's harness case study](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering),
17February2026, emphasizes trace-informed changes, comparing output to the requested
task and reconsidering repeated approaches. We retained old results, traced actual
mismatches and changed the plan. Its benchmark gains are not predictions for this
app or proof of the student's understanding.

## Actual sequence and evidence

1. Read the current source/harness and preserve the owner's new brief. Freeze a
   common six-person scenario before parent rating/new review; sourcing/discovery
   already began, so do not call the whole pass preregistered.
2. Run fresh-context, bounded source audit, product research and alternative
   discovery. Parent verifies important claims rather than counting agreement.
3. Compare North/East/West. Fresh design review rejects premature acceptance and
   asks for a minimal spatial control, real room/sofa tasks and complete lifecycles.
4. Add Delta and a capacity-fit mechanical spike. One frozen ring candidate is
   tested; failures of baseline capacity and old-target compatibility remain visible.
   Six controls cover named valid/invalid cases, not every possible grader error.
5. Contextual design review finds room/house revocation ambiguity, missing huddle
   lifecycle, fake contingency cuts, unclear presenter handoff and mixed image/text
   comparison claims. Parent preserves the preimage and fixes those sections.
6. A separate fresh technical review checks the prototype/source/replay/privacy
   boundaries. Final contextual design closure confirms only the affected paper
   corrections. Human value and implementation acceptance stay open.

The source researcher initially carried a broad beta caution from gogh news. Parent
found the current Chat FAQ and the researcher corrected it. Current Watch Party
also documents no playback sync. These are examples of useful critical checking,
not claims that every researcher error was discovered.

## What was not an A/B test

The layout spike is a matched mechanical comparison. The alternative walkthroughs
and independent critique are model-assisted design review. The live Overview was
one native visual audit. No intended-friend experiment, physical-device test,
agent-prompt effectiveness trial or new production resource run happened here.
A new prompt A/B was not needed to claim an owner-required product-contract change;
no universal gain from more instructions, agents or repeated loops is claimed.

## Carry-forward lesson and stopping condition

For substantial spatial features, require a named user task, useful effect,
audience, capacity and lifecycle, with a credible minimum/global-tool alternative.
Record when the spatial form merely adds friction. This is a project routing/gate
for the observed failure, not a mandate to invent an experiment for every chair.
Retire or revise it if the product loses its spatial interaction premise.

Stop this research lane after source/record verification, meaningful review
refinements and a bounded prototype plan. Further identical opinions do not settle
whether the bedroom is useful. The next evidence is task observation under matched
content/permissions, then affected implementation checks if that direction holds.
