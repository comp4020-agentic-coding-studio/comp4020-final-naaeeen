# Evidence and writing method

For each consequential choice record the user need or failure, observation,
alternatives, chosen action and reason, changed files, verified result, limits,
review finding, human feedback if any, and actual commit/compare links when a
real code repository exists. Preserve dates and conditions.

Use concrete examples to explain implementation decisions. Keep the living
research register separate from the short handoff and final narrative. Do not
invent tests, trial counts, users, feedback, personal reflection or history.
Historical A2 examples illustrate a method only.

Use concise connected prose and plain headings. Treat user assumptions as inputs
to examine, not facts to prove. Distinguish enforceable promises from judgements
that need real people. Necessary qualifications support a decision; repeated
generic warnings and implementation jargon in product flows usually do not.

Keep English in runnable code, active harness and reusable templates. Chinese
research/design notes remain in this separate planning workspace. Student
`README.md`/`PROCESS.md` and reflections must reflect their own position and work;
help draft from supplied reasoning rather than manufacturing experience.

Review document links, diagrams, source dates and claim boundaries. Code needs
its relevant tests and browser evidence. A prose edit needs consistency checking,
not made-up application coverage.

and `docs/review/process-comparison/`, stored as attributed reference material.
