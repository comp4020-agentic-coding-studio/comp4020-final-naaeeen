# Evidence and writing method

Active A3 procedure, revised7October2026. Read with repository docs/harness/REPORT.md.
ALWAYS return to applicable sections at each phase, section and substantial
subsection; record actual evidence, comparisons, reviews and refinements in
docs/revisit/REGISTER.md. Historical references below do not supply current results.

For each consequential choice record the user need or failure, observation,
alternatives, chosen action and reason, changed files, verified result, limits,
review finding, human feedback if any, and actual commit/compare links in this
canonical WSL code repository. Preserve dates and conditions.

Use concrete examples to explain implementation decisions. Keep the living
research register separate from the short handoff and final narrative. Do not
invent tests, trial counts, users, feedback, personal reflection or history.
Historical A2 examples illustrate a method only.

Use concise connected prose and plain headings. Treat user assumptions as inputs
to examine, not facts to prove. Distinguish enforceable promises from judgements
that need real people. Necessary qualifications support a decision; repeated
generic warnings and implementation jargon in product flows usually do not.

Keep English in runnable code, active harness and reusable templates. Original
source resources may use any language; all new A3deliverables are English. Student
`README.md`/`PROCESS.md` and reflections must reflect their own position and work;
help draft from supplied reasoning rather than manufacturing experience.

Review document links, diagrams, source dates and claim boundaries. Code needs
its relevant tests and browser evidence. A prose edit needs consistency checking,
not made-up application coverage.

Inherited examples: A2 `docs/PROCESS-EVIDENCE.md`, `docs/IMPLEMENTATION-RESEARCH.md`
and `docs/review/process-comparison/`, stored as attributed reference material.

## Per-subsection A3 record

Use docs/harness/CHECKPOINT-TEMPLATE.md for every substantial register entry.
Record comparison type and conditions, reviewer context, source/diff version,
actual checks, failed/aborted outcomes, parent reconciliation and exact commits.
Retrospective audits never rewrite chronology. Report model judgements, real
browser tasks, synthetic load and human studies separately. Keep raw private
fixtures/logs/credentials out of commits; sanitised evidence must remain sufficient
to check the claim. Update current handoff and active guidance for observed gaps.
