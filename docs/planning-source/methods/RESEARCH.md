# Research method

Start from a concrete decision and what observation would change it. Read the
actual applicable brief and project artifacts before expanding the search.

For each decisive source record its title, original URL, owner, date/version,
access date, relevant section, supported claim, limitations and design consequence.
Primary documentation can establish documented capabilities, not measured
performance on our device. A store description establishes a developer's claim,
not that we played it or that its benefits were independently validated.

Verify unfamiliar or changing APIs against the installed or proposed version.
Prefer original developer material and source code for implementation facts.
Identify excerpt-only access and unresolved conflicts. Distinguish observed fact,
documented behaviour, inference, proposed choice and future experiment locally.

Use independent lanes for separable questions, with bounded scope and expected
evidence. The parent reconciles claims and reads decisive passages. Keep expensive
research proportional to the decision; stop a lane when its uncertainties are
resolved. Broaden when a materially better route remains unexamined.

For assets and templates use `ASSET-AND-CODE-REUSE.md`. For comparisons use
`COMPARISON-AND-REVIEW.md`. Preserve failed approaches and source limits that explain
a consequential decision, without treating a long bibliography as quality.

Inherited references: `../reference/a2/docs/harness-research/REPORT.md`,
`../reference/a2/docs/harness-research/sources.md` and the A2 implementation record.
They are dated evidence; refresh claims used in a current technical choice.
