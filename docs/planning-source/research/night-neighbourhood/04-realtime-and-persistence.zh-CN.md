# 夜间居民区：实时协作、身份与持久化研究

核查日期：2026 年 10 月 6 日。本文区分课程固定要求、官方文档行为、架构建议与本地原型观察。正式 Assignment 3 仓库及其 Dockerfile、fly.toml、spec 和 CI 尚待核对；这里不把一个新技术栈写成已有工程事实，也不提供未经验证的生产数据库迁移。

## 1. 架构应该解决的产品问题

建议以一个同源网页应用完成小院：浏览器负责 3D / 2D 展示，服务器决定谁能修改什么、保存语义状态并分发改变。服务器不为每帧渲染 3D，也不需要为每个家具模型调用外部服务。位置、作者部件、配色与版本作为小数据同步；模型与纹理是可缓存的静态文件。

正式版本的候选组合是 **受支持的 Node.js LTS、Express 5、Socket.IO 4、SQLite 与 better-sqlite3**，部署到课程的一台 Fly Machine，数据库存放在其持久卷。理由是把网页、命令处理、实时通道与事务保持在一个进程边界，便于两周内完成完整流程。版本、原生模块构建和课程运行约定仍须在真实仓库里验证并锁定。这是建议，不是宣布这些组件已安装或性能已达标。

课程只固定一台小机器、一个持久卷、多人可区分、约一秒自动更新及重启重新部署后的保留；它允许 WebSocket、SSE 或足够快的轮询，未指定 Express 或 Socket.IO。[课程正式 brief](https://comp.anu.edu.au/courses/comp4020-agentic-coding-studio/assessments/final-project/)

## 2. 实时传输候选为什么不同

| 方案 | 对本项目实际帮助 | 需要自己完成的部分 | 当前判断 |
| --- | --- | --- | --- |
| HTTP 命令 + Socket.IO | 双向事件、ACK、重连与分组发送已有接口，适合加入持续协作和短暂在场信号 | 身份、每次权限检查、幂等、事务、版本、历史与一致快照 | 正式版本优先候选；不要把传输恢复当数据库恢复 |
| HTTP 命令 + SSE | 服务器推送状态，浏览器以 HTTP 提交修改；分离简单，本地原型已采用 | 与上列相同的业务可靠性；事件编号、重连与命令待定状态仍要设计 | 若最终核心只有离散部件编辑，也完全可以成为正式选择 |
| 原生 WebSocket / ws | 较低层、传输控制直接 | 应用级 ACK、重连、分组、心跳与协议细节更多 | 已有熟悉实现才优先；没有证据表明我们需要这层控制 |
| 快速轮询 | 实现容易理解，课程允许 | 更新延迟与请求成本的实际测量、版本增量与掉线提示 | 可作为窄功能备选，但不能仅凭设置 1 秒定时器宣称约 1 秒到达 |

SSE 是服务器到浏览器的持续事件流，属于网页平台原生机制；其自动重连并不会自动让数据库写入幂等，也不会建立作者权限。[HTML 标准：Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)

若真实仓库已有 Fastify 或其他合理服务器，应先比较迁移成本，不为上述推荐重写已有基础。Express 5 有破坏性路由匹配等变化，使用旧教程时需要按实际版本核对，而不是把“Express”当成跨版本完全相同的 API。[Express 5 迁移说明](https://expressjs.com/en/guide/migrating-5/)

## 3. Socket.IO 提供与不提供什么

官方文档保证成功抵达的消息按发送顺序交付，但默认消息抵达语义是 **at most once**。断线时已发送的数据可能没有收到，服务器不会自动永久保存所有事件；客户端重试和 ACK 也不能消除重复执行。官方给出的增强模式包括事件唯一 ID、数据库事件和客户端 offset。[Socket.IO delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

连接恢复是便利功能而不是一致性底座。恢复有时间范围、可能失败，而且进程重启后内存恢复状态不能当作持久数据库。建议所有客户端都具备从授权快照重新建立状态的路径。如果启用恢复，设定与现有身份检查一致的策略；特别不要随意采用 skipMiddlewares，因为恢复时跳过鉴权可能使断线期间已被移除的成员重新进入。[Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)

连接 middleware 每条连接只运行一次。一个用户连接后可能被移除、小院可能关闭、会话可能撤销，因此每个持久修改都需要检查当前授权。[Socket.IO middlewares](https://socket.io/docs/v4/middlewares/)

Socket.IO room 是服务器维护的发送频道。它适合把小院变化送给正确会话，但不自动知道谁拥有小院；加入频道前需检查成员资格，移除成员后需撤销订阅并断开不再合法的连接。[Socket.IO rooms](https://socket.io/docs/v4/rooms/)

## 4. 需要保存与不需要保存的状态

| 状态 | 建议是否持久化 | 为什么 |
| --- | --- | --- |
| 居民身份、会话摘要、成员资格、邀请状态 | 是 | 返回时能被区分，撤销与权限不能随重启失效 |
| 个人房间模板、家具目录 ID、变体、逻辑位置与旋转 | 是 | 是用户的持续创作，而非一帧画面 |
| 共同作品、作者部件、当前内容、版本与撤回标记 | 是 | 错时接续、作者权限与冲突判断都依赖它 |
| 经用户主动保存的语义档案 | 可选，纳入范围时保存 | 档案是明确选择，需有可见性与撤回规则 |
| 命令回执与事件序列 | 有限保留 | 区分已提交但 ACK 丢失、重复提交及落后客户端 |
| 正在拖动的预览、光标、短暂连接 / 角色位置 | 通常否 | 高频、过期即无意义，持久化会增加成本和错误暗示 |
| 用户自愿设置的“欢迎招呼 / 想安静” | 可设置期限后保存 | 是本人表达，与连接在线状态分开 |
| 最后在线时间、累计在线分钟 | 第一版不收集 | 不是核心需要，也容易把空间变成活动监控 |

推荐实体可包括居民、会话、成员、邀请、房间、摆设、共同作品、贡献、事件、命令回执和迁移记录。私人信件和礼物应等相应产品流程确定后再加入，不提前扩展整套数据库。数据库只保存逻辑状态；Three.js 场景对象、GPU 纹理、摄像机瞬时值不成为持久格式。

## 5. 一次可靠修改应怎样完成

以“把自己的灯罩改成绿色”为例，推荐采用以下业务顺序。这是设计契约，不是目前正式服务器代码已经实现的功能。

1. 客户端生成命令 ID，记录具体操作、目标 ID 与预期对象版本。界面显示待保存，并保留同一个 ID 到最终结果明确。
2. 服务器从可信会话推导居民身份；不接受客户端直接声称自己是某个作者。
3. 检查当前小院成员资格、目标归属、内容大小、目录 / 配色允许值与限流。
4. 根据居民与命令 ID 查找回执。同一 ID 同一内容返回既有结果；同一 ID 不同内容明确拒绝，不能执行另一项操作。
5. 在同一数据库事务内检查预期对象版本，应用修改，增加版本，记录授权流中的事件和命令回执。
6. 提交成功后发 ACK 和对应广播。提交失败时不给“已保存”的成功回应。
7. 客户端从 ACK 或授权事件确认结果；ACK 丢失时重试原命令，而不是每次新建 ID 再执行。

不同作者修改不同部件一般可以独立成功，避免整院版本把无关操作都变成冲突。两台设备改同一作者部件时，应展示“版本已改变”，重新读取并让人选择继续；第一版不需要自由文本 CRDT，但也不能默默让最后写入覆盖另一份内容。移动家具则在同一事务检查房间边界、碰撞和固定障碍，不能只依赖本地红色预览。

命令回执的保留期限和客户端重试期限要一致。如果服务器已经删除旧回执，就不能对任意久远的重试宣称永远恰好一次。第一版宜定义有界重试窗口、过期后的明确结果查询或重同步，再决定精确保留天数。

## 6. 快照、增量与断线后的状态一致

每个授权的数据流需要自己的单调序号。例如一个小院公开流和某个居民私人收件流不能共用一个全局序号，却只给客户端发送其中一部分；否则合法过滤造成的缺号会被误认成丢包，也会暴露无关活动线索。

初次或无法恢复时，服务器从一致读视图返回快照及其序号 S。同步过程中要处理随后发生的事件：先建立受权订阅并缓冲，再把大于 S 的事件按顺序交给客户端，或者采用等价的可靠握手。若快照读取和订阅之间留一个空档，该空档中的修改可能永远看不到。

客户端丢弃已经应用的重复事件，发现真正缺号就请求补齐或重取快照；事件超过保留窗口时直接取新快照。还需要授权流的当前序号 / 水位检查：如果丢的是最后一条事件，没有下一条触发缺号，仅靠检查跳号会永远停在旧状态。

断线 UI 应保留未确认的草稿和命令，不把它们混进“服务器已保存”的画面。重连后先恢复一致状态，再重新提交仍有效的待定命令。恢复不成功时给明确提示和可继续路径。让窗口保持原位置是体验目标，让版本一致是业务正确性目标，两者不要混为一项检查。

## 7. 昵称、邀请与身份恢复不是一回事

昵称是展示信息；邀请是获得成员资格的能力；会话凭据证明当前请求是谁。这三者不能互相替代。共享邀请链接后进入的人可以成为不同居民，但不能凭知道 Alice 这个昵称就接管 Alice 的房间。

建议第一版使用伪名身份与服务器生成的高熵不透明会话，同源 HttpOnly、Secure、SameSite 合理配置的 cookie 携带会话，数据库保存其摘要与到期 / 撤销状态。具体 CSRF 方案应结合 HTTP 命令、Origin 校验和 cookie 策略定稿；Socket 连接也检查来源，并且每次修改检查当前会话和成员资格。

跨设备与清除浏览器数据后的恢复可以提供高熵恢复码，由用户主动保存；服务器保存摘要、支持轮换并明确恢复码的用途。这样仍需向使用者解释：清除 cookie 而没有恢复码时，不能只靠输入旧昵称证明身份。恢复流程、邀请预览、退出与撤销都是实际用户路径，应有相应检查。邮箱 / 第三方登录也可作为未来选择，第一版没有必要为了昵称房间先引入完整账户平台。

## 8. 可见性、删除与日志

服务器在快照读取、增量回放、加入频道及每次修改时都执行授权。私人信件若未来加入，仅发送到合法收发者，不能先广播给所有客户端再由前端隐藏。移除成员时停止后续公开和私人订阅，并定义已有草稿、贡献、档案还如何处理。

作者撤回可能涉及当前作品、历史事件载荷、档案和备份。建议将内容与留痕分离：作品可保留“作者撤回了一片”的无内容标记，重放和历史读取也不再返回撤回内容。备份的保留与恢复操作需要遵循同一约定；恢复较旧备份后应重新应用删除 / 撤销记录，不能让撤回内容悄悄回来。第一版的删除语义必须写清，不能同时承诺永久不可改历史与随时彻底删除。

运行日志记录必要的请求 / 命令 ID、结果码、耗时、错误类别与低敏实体关联，用于查“为什么没保存 / 为什么另一个窗口没更新”。不记录 cookie、恢复码、邀请明文、私人消息全文或每帧光标。日志与持久事件是不同用途，不应为了排错把所有用户创作无限期复制一份。

## 9. SQLite 和 better-sqlite3 的实际取舍

better-sqlite3 提供同步 API、事务与在线备份接口，需要受支持的 Node.js，原生二进制可用性依赖平台与版本。它的官方性能宣传不是我们的小 Fly Machine 已测性能；短而有界的事务较适合当前小院，长查询和高频大批写入仍可能阻塞主线程。[better-sqlite3 官方仓库](https://github.com/WiseLibs/better-sqlite3)

建议在生产预检中固定 Node、包版本与镜像，并验证 Linux 镜像里的原生模块安装。SQL 全部参数化，事务只做短数据库工作，不夹杂网络请求或模型加载；限制单次读取范围，按成员、小院、对象和事件序号建立必要索引。大导出或以后出现的长查询才考虑独立任务 / worker，不提前改成多服务架构。

WAL 是值得考虑的性能模式，但需检查**实际链接的 SQLite 引擎版本**。官方报告罕见 WAL-reset bug 在 3.51.3 及之后修复，另有 3.44.6、3.50.7 回补；风险与多个连接同时写入 / checkpoint 有关。不能只看 better-sqlite3 的 npm 版本就假定引擎已修复。[SQLite WAL 官方说明，第 11 节](https://sqlite.org/wal.html)

WAL 下 synchronous=NORMAL 在应用崩溃与断电持久性之间有区别：已提交事务可能因系统崩溃或断电回滚；FULL 在每次提交增加 WAL 同步。建议第一版优先 WAL + FULL、短事务与一次写连接，在实际小机器上测延迟，再决定是否接受其他耐久性取舍。这不保护卷本身损坏，也不替代备份。[SQLite synchronous 官方说明](https://sqlite.org/pragma.html#pragma_synchronous)

Node 内置 node:sqlite 也应作为候选，而不是因名字带“内置”就认定成熟度与接口适合。网页工具未能访问 Node 24 页面后，父任务通过 Node fetch 读取了官方 **v24.15.0 tag 的 sqlite.md**：该版本变更条目与 Stability 都明确为 Release candidate。这个状态与本地运行版本相符；生产采用其他版本时仍应重查接口和引擎。better-sqlite3 也需要原生模块构建验证，选择它不是宣称内置方案不可用。[Node v24.15.0 官方源文档](https://github.com/nodejs/node/blob/v24.15.0/doc/api/sqlite.md)

## 10. Fly 上数据库真正应放在哪里

Fly Machine 根文件系统是临时的；SQLite 主文件、WAL 与相关持久状态要位于同一个挂载卷目录。卷固定到一台物理服务器与一个区域，只能关联一个 Machine；Fly 不自动在多个卷之间复制数据。一台机器一份卷意味着部署、宿主机或网络故障可以造成停机，不能承诺高可用。[Fly Volumes overview](https://docs.fly.io/volumes/overview/)

非常关键的一点是 **release_command 的临时 Machine 没有挂载持久卷**。不要照抄托管 PostgreSQL 示例，把这里的 SQLite 迁移放到 release_command；迁移必须在有卷的正式启动路径执行，完成之后才允许 readiness 和业务请求。[Fly app configuration：release_command](https://docs.fly.io/reference/configuration/)

建议启动顺序为：确认卷路径存在且可写，打开数据库，检查引擎版本和完整性 / 迁移状态，在适当事务中运行编号迁移，成功后开始服务；失败保持可诊断的未就绪状态。不要遇到读库失败就用初始数据覆盖旧库。部署策略要适配单卷单机，不能把 canary / blue-green 当成能共享同一 SQLite 卷的默认模式。实际策略必须依据真实 fly.toml 和课程约定核对。

模型、材质与代码随镜像提供，用户作品随卷保存。发布新素材时保留稳定目录 ID 和旧版本解析，或做明确迁移；否则数据库虽未丢失，用户家具也可能因删除旧文件而消失。服务优雅关闭尽量停止新写入、完成短事务并关闭连接；无论是否正常退出，返回时仍以持久快照恢复，不能依赖进程内房间列表。

## 11. 备份应证明能恢复什么

不要直接复制正在 WAL 写入的单个 .db 文件，忽略尚在 WAL 的内容。SQLite 官方提供在线备份 API 与 VACUUM INTO 等一致备份途径；better-sqlite3 有 backup 接口，可在运行中创建可重新打开的 SQLite 备份。备份完成的语义以采用的接口为准，不把每一种增量备份都解释为同一瞬间的快照。[SQLite Backup API](https://sqlite.org/backup.html)、[better-sqlite3 backup API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md)

建议第一版的运维约定包括：部署前完成可读备份；定期创建一致备份并检查结果；在用户授权的离卷位置保存副本；保留适当期限；至少在隔离位置恢复一次并验证居民、作品、权限、撤回与关键回执。仅放在原卷的备份能帮助撤销误操作，却无法抵御整卷损失。Fly 日常自动快照可能不含最新数据，官方也不建议把它当唯一主备份。[Fly 卷备份边界](https://docs.fly.io/volumes/overview/)

实际备份频率、允许损失多少分钟的数据和恢复时间是运维选择，尚未通过本项目测量。无需在两周内搭建多地区复制，但应清楚记录这台课程服务器能保证什么，以及单点故障后怎样恢复。

## 12. 本地原型已经证明了什么

当前[视觉比较原型](../../prototypes/visual-comparison/README.md)的 manifest 只声明 Three.js 0.186.1。它使用纯 Node HTTP、SSE、演示居民身份与小 JSON 状态文件，不含正式 Express、Socket.IO、SQLite、真实邀请或生产会话。

它有意义地检查了共同逻辑状态能够驱动不同渲染方案：家具按作者修改、移动与转向；共同灯罩的两个作者部件分别变化；事件推动另一个窗口更新；JSON 状态重新读取后保留内容。父任务还通过真实浏览器验证两会话更新和本地服务器重启保留。证据与截图应以最终 evaluation 记录为准，不把这些观察扩大为 Fly 重部署、持久卷故障、真实身份安全或生产延迟的验证。

研究原型里显式传入 Alice / Bob 便于比较画面，不是保护作者所有权的真实安全模型。把其文件复制进正式应用前，必须替换身份边界、持久格式与恢复契约；并保留已经发现的固定障碍碰撞、版本和幂等测试价值。

## 13. 正式实现前后应验证的场景

| 场景 | 要观察的真实结果 | 不能替代它的证据 |
| --- | --- | --- |
| 两个独立浏览器操作不同贡献 | 两项成功，另一会话无需刷新看到改变 | 单页截图或直接改内存 |
| 同一部件的旧版本修改 | 明确冲突，已保存内容不被覆盖 | 只测正常顺序操作 |
| 写入已提交、ACK 丢失、原命令重试 | 一次业务效果，返回一致结果 | 每次重新生成命令 ID |
| 断线间发生变化并重连 | 从正确快照 / 增量恢复，没有永久遗漏 | UI 显示“已连接” |
| 成员连接后被移除 | 后续读取、修改与订阅失效 | 仅测试登录时检查 |
| 私人内容读取与广播 | 其他成员不会在网络载荷收到内容 | 前端隐藏卡片 |
| 进程异常退出、重启、实际重新部署 | 合法已保存作品仍存在 | 本地页面 reload |
| 迁移失败、目录换版 | 不覆盖旧数据；失败可诊断，旧作品仍可解析 | 空库上的首次启动 |
| 独立备份恢复 | 内容、身份、权限、撤回与版本一致 | 看见一个 backup 文件 |
| 慢连接、手机尺寸与键盘 | 待定状态清楚，核心操作可完成 | 桌面渲染帧率 |

课程约一秒更新需要在部署环境中测“服务器接受修改到其他开放会话实际显示”的完整链路。不能只测 socket.emit 调用耗时或本机 HTTP 回包；同步阈值、样本、地点与失败都需报告。单机性能测量再决定允许同时多少成员，而不是把设计中的 8 或 12 人写成已验证容量。

## 14. 尚未解决的决定与来源边界

- 正式仓库、运行镜像、包管理器、现有 checks 与 Fly 配置是什么？先读取再落栈，不能从 A2 推导。
- 共造核心是否需要双向长连接，还是 HTTP + SSE 已足够？按正式使用流程与原型检查选择，避免为技术名字迁移。
- 会话与恢复码期限、邀请使用次数、成员被移除后的贡献保留，必须与产品契约一致。
- 命令回执、事件、删除标记和备份各保留多久？明确边界后再选清理策略。
- Linux 镜像中实际 better-sqlite3 / SQLite 版本、WAL 耐久模式与小机写入延迟，需要工程预检。
- 真实备份位置、恢复流程及部署停机时间待确定；本次研究没有创建云服务、安装生产数据库、处理密钥或发布应用。
